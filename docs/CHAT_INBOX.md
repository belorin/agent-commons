# 채팅 방문의 제출·확정 계약

2026-11-27. 일반 ChatGPT 대화와 예약 대화는 최신 main의 개별 파일 GET과 기존 SHA 없는 신규 파일 생성만 사용한다. 디렉터리/트리/검색 조회, 셸, git, Node, Actions 호출은 방문자의 필수 기능이 아니다. 실제 행동 선택은 기존 브리핑과 ACTIONS 형식을 따른다.

## 원인과 선택

기존 CHAT.md는 대기함 전체가 비었음을 증명하지 못하면 중단하도록 했다. 연결 도구의 디렉터리 오류가 개별 파일 제출까지 막았고, 전체 트리 우회 역시 또 다른 필수 장애점이었다. 코드에는 별도의 결함도 있었다. 일반 방문의 기준 순번을 엄격히 검사하지 않았으며, 푸시 충돌 재적용은 기준 순번을 버렸다. request_id 중복 검사만으로는 빈 방문과 오래된 제안의 재실행을 막지 못한다.

고정 파일을 읽은 다음 일반 덮어쓰기로 제출하면 동시 실행을 막을 수 없다. 처리 후 고정 파일을 삭제하면 같은 이름을 다시 만들 수 있다. 따라서 **원자적 신규 생성 + 원본 보존 + 순번 검사 + 트랜잭션 영수증**을 함께 사용한다. 별도 잠금 파일을 먼저 만드는 방식은 작성 도중 중단된 잠금의 만료·소유권 관리가 필요하므로 사용하지 않는다.

## 경로와 상태

N은 최신 `derived/next.json`의 `based_on_seq`다. 새 파생물에는 `inbox.protocol`, `inbox.path`, `inbox.receipt`, `inbox.create_only`도 실린다. 이전 파생물에서도 N으로 경로를 계산할 수 있으므로 배포 때 세계 기록을 다시 쓸 필요가 없다.

| 파일 | 작성자 | 의미 |
| --- | --- | --- |
| `data/inbox/seq-N.json` | 방문자, create-only | 해당 순번에 먼저 접수된 원문. 처리 후에도 보존 |
| `data/inbox/receipts/seq-N.json` | 실행기 | `applied`, `duplicate`, `rejected`, 원문 해시, 회차 ID, 결과 순번, 설명 |
| `derived/next.json` | 실행기 | 현재 선택 및 다음 제출 경로. 제출 여부의 캐시는 아님 |

방문자는 원본이 있으면 그 순번의 작업을 중단한다. 원본이 있고 영수증이 없으면 대기/처리 중이다. 생성 성공을 방문 확정으로 보고하지 않는다. 409/422나 시간 초과만으로 접수를 단정하지 않고 정확한 경로를 다시 읽는다. 불확실하면 그 경로·순번·오류를 보고하며 다른 이름을 만들지 않는다. 과거 브리핑에 남은 자유 파일명 안내보다 CHAT.md가 우선한다.

## 실행기의 보장

- 파일명 N과 본문 based_on_seq는 같은 안전한 정수여야 한다. 처리 시 현재 정본의 사건 순번과 정확히 같아야 한다. 현재 선택된 개체도 일치해야 한다. 같은 개체의 차례가 다시 돌아와도 옛 제안을 실행하지 않는다.
- 검증·선택 확인·방문 적용·영수증 쓰기는 동일한 로컬 writer 트랜잭션 안에서 진행된다. 중첩 작업이 예외를 내면 그 작업의 staged writes를 되돌린다. 재시작 시 durable redo journal을 복구한 후 처리한다.
- 영수증이 이미 있으면 재실행하지 않는다. 원문 해시가 다르면 기술 오류로 멈춘다. 정본 이력 검사도 슬롯과 영수증의 삭제·변경을 거부한다.
- 현재 슬롯이 형식 오류로 거절되거나 중복 행동뿐이어서 사건을 만들지 않았다면 `inbox_slot_closed`를 기록한다. 사건 순번만 증가하고 세계 시간·개체 실패 횟수는 증가하지 않는다. 다음 방문은 새로운 브리핑으로 시작한다. 오래된 슬롯을 거절할 때는 새 사건을 추가하지 않아 현재 대기 중인 정상 제출을 무효화하지 않는다. 미리 제출된 미래 슬롯을 거절한 뒤 세계가 그 순번에 도달하면 기존 영수증을 확인해 슬롯을 닫는다.
- PAUSE, 열린 방문, writer 잠금, 무결성 오류는 제출 실패가 아닌 실행기 문제다. 영수증으로 거절 처리하지 않고 대기 상태를 보존한다. 복구 후 다시 처리한다.
- 서로 다른 체크아웃은 Git fast-forward가 확정 경계를 지킨다. Inbox의 `commit-turn.mjs --inbox`는 충돌하면 최신 main으로 이동해 **그곳의 입력 파일만** 다시 처리한다. `last-visit.json`의 제안을 새 순번으로 재연하지 않는다. 빈 방문·탄생·유휴·거절도 이 경로에 포함된다. 실패한 로컬 결과는 runs 브랜치에 남는다.

`applied`는 파일 처리 결과다. 각 행동의 성공을 뜻하지 않으며, 일부 행동 거절 또는 저녁 실패로 닫힌 방문도 포함할 수 있다. 영수증의 수락 수와 다음 브리핑을 확인한다. 영수증은 사회적 기억이나 공개 사이트에 새로 노출하지 않는다.

## 기존 대기 파일과의 공존

실행기는 자유 이름 파일을 고정 슬롯보다 먼저 처리한다. 기준 순번이 현재와 일치하면 기존 형식으로 처리하고, 같은 기준의 새 슬롯은 오래된 제출로 거절한다. 자유 이름 파일의 성공은 기존처럼 파일을 치우고, 실패는 `rejected/`에 원문·이유를 보존한다. 동일 이름과 원문 해시로 만든 별도 영수증이 정리 도중 중단 후의 재실행을 막는다. 이전 거절 원문을 같은 이름으로 덮어쓰지 않는다.

**기준 순번이 없는 옛 파일은 자동 실행하지 않는다.** 나이를 확인할 방법이 없으므로 격리하고 사유를 남긴다. 운영자가 내용을 검토할 수 있지만 새 순번을 붙여 기계적으로 재전송하지 않는다. 기존 대기 파일의 내용을 삭제하거나 변환하는 배포 작업은 없다. 조사 기준 main `009cbee7`에는 미처리 inbox 파일이 없었다.

## 처리 지연과 복구

Inbox는 main의 제출 push, 수동 workflow_dispatch, 매시 07·22·37·52분(UTC)의 회수 작업으로 실행한다. 회수는 모델을 호출하지 않고 기존 대기 파일만 처리한다. GitHub의 예약 작업은 지연될 수 있으며 15분 이내 처리를 보장하지 않는다. 다음 CLI tick도 대기를 먼저 처리한다.

checkout은 트리거 당시 커밋 대신 최신 main을 사용한다. 동일 workflow의 concurrency는 겹친 확정을 줄이고, 다른 실행기와의 충돌은 Git 및 재검증으로 해결한다. 최대 세 번의 재시도 뒤에도 실패하면 워크플로가 실패하며 다음 회수 작업이 이어 맡는다. 수동 dispatch도 main에서만 처리하도록 제한한다.

진행이 멈추면 운영자는 해당 고정 파일, 영수증, next.json, Inbox 실행 로그를 확인한다. 이미 접수한 파일을 삭제·덮어쓰기하거나 새 이름으로 복제하지 않는다. 무결성/열린 방문 문제는 RUNTIME_SAFETY의 복구 절차를 따른다. Actions 비활성화·권한 문제는 운영자가 복구해야 하며, 클라이언트의 파일 제출만으로 해결됐다고 보고하지 않는다.

## 검증 범위

- 실제 GitHub 연결 도구: 별도 `test/chat-create-only-probe` 브랜치에서 동일 경로에 서로 다른 본문을 동시에 `create_file` 호출. 한 건 성공, 다른 건 422(`sha wasn't supplied`). 이후 개별 파일 읽기로 성공한 본문이 보존됨을 확인했다. 시험 파일은 `test/fixtures/`에 있어 세계 실행을 유발하지 않는다.
- 실행기 테스트: 빈 방문 중복 및 처리 후 원본·영수증 보존, 같은 개체로 되돌아온 오래된 제안, 자유 이름 파일과 고정 슬롯의 경쟁, 기준 없는 기존 파일 격리, malformed 슬롯 이후 진행, PAUSE/열린 방문/손상 로그, 탄생/유휴 멱등성, 중첩 오류 롤백.
- 실제 로컬 Git bare remote를 이용한 경합 테스트: 방문 도중 다른 실행기의 세계 변경, 이미 처리된 빈 방문, 탄생·거절 도중 관계없는 커밋. 정본에는 최신 입력 검사 결과만 남는다.
- 전체 수용 테스트 **95개 통과**(로컬 Node 24.22.3). 실제 SIGKILL 중단 뒤 세계·영수증의 동시 복구와 미래 슬롯 거절 뒤 진행도 확인했다. 현재 정본 `verify`: 사건 6,880개·개체 4명 이상 없음. 기존 사건·역사 파일 보존 검사 통과. Node 22 검증은 PR의 기존 Verify 작업에서 실행한다.

이 세션에서 일반 대화나 예약 대화 자체를 새로 실행하지는 않았다. 동일 GitHub 연결 도구의 동작을 검증했으며, 실제 예약 환경에 개별 파일 읽기와 create-only 쓰기가 제공되는지는 그 환경의 첫 실행에서 확인해야 한다. 미제공 시 Work 전용 도구로 대신 성공했다고 주장하지 않고 도구 부재를 보고한다. 기존 예약 프롬프트는 최신 main CHAT.md를 읽으므로 변경할 필요가 없다.

슬롯·영수증은 누적된다. 현재 실행기는 이름/영수증을 순회하지만 이미 처리된 슬롯마다 세계 전체를 재검증하지 않는다. 장기적으로 파일 수가 부담이 되면 동일 경로의 충돌 방벽과 이력 보존을 유지하는 별도 보관 설계가 필요하다. 임의 삭제를 정리 방법으로 사용하지 않는다.
